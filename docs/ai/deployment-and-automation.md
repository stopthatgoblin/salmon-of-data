# Low-cost publication and unattended updates

Recommendation and implementation status, 6 September 2026.

## What is ready, and what is not

Ready locally: the three-page dashboard, frozen v1 registry, historical snapshot, audited calculations, 2026 Data Calendar, and a genuine static export. `npm run build:static` generates public HTML, browser JavaScript and downloads in `dist/client`. `wrangler.static.json` configures an assets-only Cloudflare deployment. The original `npm run build` Worker build remains available.

Not activated or implemented end-to-end: GitHub repository, Cloudflare account connection, domain, scheduled actuals refresh, release archive, change notification delivery, and live calendar import. The calendar JSON is a checked September 2026 schedule, not a claim that an importer has run. The existing downloader captures inputs only; the existing builder still recreates the frozen review edition. Do not schedule that builder unchanged and expect new observations.

## Recommendation and cost

Use a public GitHub repository, standard Linux GitHub Actions runners, Cloudflare Workers Static Assets, and GitHub Releases for source-vintage archives and update notifications. No application server, database, paid data provider or runtime AI call is needed. The normal expected hosting/compute cost is £0 within free service terms; a custom domain is the optional recurring purchase. Start on the free `workers.dev` address before buying a domain.

Cloudflare static-asset requests are free and unlimited. This is specifically an assets-only deployment: rendering HTML in a Worker would instead invoke Worker limits. Cloudflare's own optional build service includes 3,000 free build minutes/month. Public-repository Actions on standard GitHub-hosted runners are free; private repositories have metered allowances. Use Linux, not paid/larger runners. Prices and service terms can change.

Netlify is technically viable now using the same `dist/client` export, but its current free plan includes 300 credits/month and each production deployment uses 15 credits. Twenty deployments would consume the entire allowance before traffic or other usage. Since only changed data triggers deployment, you might fit, but Cloudflare provides more headroom. Avoid running two deployment systems for the same site.

Sources: [Cloudflare pricing](https://developers.cloudflare.com/workers/platform/pricing/), [Cloudflare build limits](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/), [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [Netlify credits](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/).

## One-time setup: from this computer to a public website

1. Create a GitHub account/repository and a Cloudflare account if needed. A public repository makes the methods inspectable and qualifies standard Actions runners for free usage. If you prefer private source, keep it private and monitor the included Actions allowance; this is your choice, not a prerequisite for the website to be public.
2. Preserve the original evidence before publication. Package `data/raw`, its source manifest and the frozen registry as the initial September 2026 archive. Store it as a GitHub Release asset with a SHA-256 manifest, and keep the local copy. Do not add the 93 MB Canadian ZIP or every future raw vintage to ordinary Git history. GitHub recommends Releases for distributing large files; individual release assets must be under 2 GiB. Keep changed files only in subsequent archives, referring to unchanged hashes, rather than attaching the same large ZIP to every daily update. Normal Actions artifacts expire and are not the long-term archive.
3. Before the first `git add`, exclude `data/raw/`, `data/incoming/`, generated archives and temporary captures in `.gitignore`. Existing ignores already cover dependencies, environment files and build output. Commit the source code, lockfile, normalized dashboard data, calendar, blog, frozen definitions, manifests and public downloads. The site build needs these files, not the full raw Canadian table. Audit jobs must download and verify the archived source files explicitly.
4. Initialize Git and push. In this project folder run `git init -b main`, `git add .`, review `git status`/the staged diff, then `git commit -m "Initial tracker and September 2026 scenarios"`. Create an empty GitHub repository without an extra README, add its actual URL with `git remote add origin <YOUR-REPOSITORY-URL>`, then `git push -u origin main`. Replace the bracketed value; no repository has been created by this task.
5. Build the website with Node 24: `npm ci`, `npx tsc --noEmit`, `node --test scripts/chart-data.test.mjs`, then `npm run build:static`. Confirm `dist/client/index.html`, the blog/calendar HTML and the downloadable data exist. `npm start` previews these assets at port 3000; `npm run preview:static` remains available at port 3001. Use this static preview rather than the experimental hot-reload server, which stalled during local review. `npm run check:site` verifies all three routes and their assets against port 3000. Only `dist/client` is public deploy output: do not publish the workspace or `dist/server`.
6. For the first Cloudflare deployment, use `npx wrangler login`, then `npx wrangler deploy --config wrangler.static.json`. The command publishes publicly to the Worker name configured in that file; inspect/change the name before running it. It returns the exact `workers.dev` URL. These commands are instructions, not actions already taken here.
7. Check that public URL directly: tracker interaction, direct `/blog` and `/calendar` navigation, refresh on each route, download links, missing-page behaviour and phone layout. Add your domain later in Workers & Pages → this Worker → Settings → Domains & Routes → Custom Domain, following Cloudflare's DNS instructions. Enable registrar auto-renew if you want continuous ownership.
8. For automation, create a Cloudflare API token limited to the required account/Worker deployment permissions and put it in GitHub Actions secrets as `CLOUDFLARE_API_TOKEN`; put the account ID in `CLOUDFLARE_ACCOUNT_ID`. Do not commit the token or use a Global API Key. The deployment step runs the same `wrangler deploy --config wrangler.static.json` command. GitHub supplies a separate short-lived `GITHUB_TOKEN` for repository commits and releases.
9. Use one deployment workflow family: human pushes build/publish code or blog changes; the scheduled data workflow validates, builds and deploys its own changed snapshot. Share the deploy job rather than also enabling Cloudflare's automatic Git builds. This avoids duplicate deployments and the GitHub-token trap described below.

## Exact unattended update sequence

This is the implementation contract for the production pipeline, replacing the earlier suggestion to approve every data pull request. Normal validated updates publish automatically. Only exceptions require intervention.

1. **Wake on a schedule.** Run a lightweight source check four times daily, for example 01:17, 07:17, 13:17 and 19:17 UTC. Allow a manual recovery trigger. The release calendar prioritizes expected sources but must not be the only trigger: agencies reschedule, and revisions can appear off-calendar. Quarterly Canada checks use table metadata/conditional requests before downloading its large ZIP. Indeed has daily observations but generally weekly publication.
2. **Fetch into staging.** Retrieve source groups with timeouts, bounded retries and a descriptive User-Agent. Save retrieval time, URL, HTTP metadata and content hash. Reject HTML/error pages disguised as CSV. An HTTP success alone is insufficient. Pair Indeed basket/all-market inputs; pair JOLTS rates and CES employment inputs. Check consistent reference periods and do not publish a partially updated pair.
3. **Detect meaningful changes.** Compare parsed observations with the last accepted capture. Ignore formatting-only changes. Separate newly added periods from revisions to existing periods. If nothing changed, skip rebuild, deployment and notification. A successful check may update a small internal heartbeat without triggering a site build.
4. **Validate before accepting.** Check schema, IDs, units, dates, unique keys, required basket membership, quality flags and calculation invariants. Missing values remain missing. New latest dates must not move backwards. Impossible values or a disappearance of history fail the source group. Genuine large economic changes should be flagged but must not automatically be rejected solely because they are surprising or disagree with a scenario. Establish any numeric plausibility thresholds before activation.
5. **Recalculate actuals.** Parameterize the current builder to read the accepted source vintage and the run's observation cutoff. Keep the baseline year, industry codes, age ranges, weights, smoothing and missing-data rules unchanged. A 2019-based metric still uses the defined mean of 2019 ratios; revisions can affect that normalization and must be retained in the vintage record. Never silently introduce a fixed denominator or switch to a ratio of annual averages. Refresh latest component labels and source dates, not just chart values.
6. **Preserve the forecast.** Load the original v1 registry read-only and verify its hash against the initial release. No automated job runs `--freeze`. Use the original anchor and 2029 endpoints even when the source revises the anchor-period actual. Such revisions may create a visible difference between the historical line and the original forecast start; that is honest and should be explained.
7. **Archive the accepted vintage.** Record new observations, revised observations, source hashes, normalized inputs, calculation version and capture times. Keep first-captured values in a separate append-only ledger. Call them *first captured*, not necessarily *first published*: polling can miss a correction between official publication and retrieval. Where exact first-release scoring matters, use a provider vintage service or capture at release time with documented limitations. Archive enough to rebuild each published edition through 2029; chart screenshots alone are insufficient.
8. **Build a coherent candidate.** Use the newest validated groups and the last good versions of unavailable independent groups. Show each metric's own observation date; record source-check failures separately. A Canadian download failure need not prevent a valid US recruitment update. Never fabricate a replacement value. Build the full site once, test its files/routes and verify frozen-path regression tests.
9. **Publish atomically.** Commit the accepted compact snapshot to the data publication record and deploy that exact commit/artifact. Serialize data and code deployments so an older job cannot overwrite a newer one. Use a concurrency group with in-progress publishing allowed to finish. If deployment fails, keep the prior public site and retry the pending artifact; do not lose the update merely because its data was already committed. Retain a last-successfully-deployed commit/hash separately from the last-fetched hash. Keep a rollback target.
10. **Notify after success.** Publish a GitHub Release/change note only after the public deployment and smoke check succeed. Include new dates, metric movements, historical revisions and a link to the site. Watch the repository's Releases for update notifications and enable Actions failure emails. No-change checks stay quiet. A source outage or missed expected release generates a deduplicated alert, not a new issue/email every six hours. Confirm the notification channel with one test before relying on it.

Use the deployment step in the same workflow (or an explicitly dispatched/reusable workflow). A commit made with `GITHUB_TOKEN` does **not** trigger another Actions workflow listening for `push`; designing around that assumption would leave the website stale. [GitHub explains this behaviour](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

## What exactly changes on the charts?

For a date t between the frozen anchor a and 31 December 2029 h, each scenario is:

`scenario(t) = original_anchor_value + (original_endpoint - original_anchor_value) × (t - a) / (h - a)`

That formula never uses the latest actual as a new anchor. The existing chart helper already implements it and draws solid actuals above the dashed scenarios. The dashed lines are retained through past and future dates for comparison; they are not erased when actuals arrive. A source gap stays a gap.

Example: August 2026 earnings are already available, but the current real-pay metric ends in July because August CPI has not been released. After the 11 September CPI release is available in the downloaded series, the pipeline calculates August earnings/August CPI, applies the unchanged 2019 indexing rule, adds the August actual and republishes. It does not label this as a September labour-market observation. Any July revision is logged separately. Canadian Q2 data released on 15 September appears at 30 June and updates the trailing-four-quarter calculation, not at 15 September.

For September 2027 scoring, compare the captured September observation with each path at that observation date; Canada uses Q3 and cannot be scored until that quarter is published. Preserve initial and revised comparisons. Matching a path supports its predicted pattern, not AI causation.

## Calendar automation

The current `/calendar` contains 11 confirmed remaining-2026 releases plus two estimated release months, with source links and affected metrics. The data lives in `data/release-calendar.json`, mirrored as a public download. Daily Indeed observations are explained above the schedule rather than given fictitious release times.

The production calendar importer should refresh the official BLS ICS schedule daily and map only CPI, Employment Situation and JOLTS to these metrics. Preserve event IDs, timezone, reference period, confirmation status and last verification time. Check the annual schedule pages if the ICS fails. The ICS request returned 403 during this local check, so successful fetching from the actual GitHub runner is a launch gate, not assumed working. If both sources fail, keep the existing dates and flag the schedule as unverified/stale; do not generate new dates by adding 30 days.

For Statistics Canada, use the next-release announcement for the detailed quarterly JVWS table, not the monthly aggregate vacancy calendar. Confirm Q3's December day when the agency announces it. For the New York Fed, retain an expected November window until an exact date is published. Never promote a customary month to a confirmed day. An automated importer must be deterministic and validated; no AI is needed at runtime. Confirmed-event changes should trigger a calendar rebuild; a mere check timestamp need not force repeated deployments. Move passed events out of Upcoming and roll to the next year's published calendar before 2027, retaining archived schedules.

## Reliability and remaining decisions

- **Not instant:** these agencies generally provide downloadable releases, not push webhooks. Six-hour polling means roughly up to six hours after the file becomes accessible, plus build time; provider mirrors and scheduler delays can add more. Poll more frequently in release windows if that latency matters.
- **Not maintenance-free:** routine releases need no approval; schema changes, discontinued series and changed definitions may need a repair. A reliable system fails visibly and keeps the last good edition. It cannot promise that every future provider change will fix itself.
- **Watch the scheduler:** GitHub schedules can be delayed/dropped and public-repository schedules can be disabled after 60 days without activity. A separate heartbeat/dead-man check should alert if there has been no successful run for 24 hours. Monitoring only from the same scheduled workflow cannot detect that workflow never starting. Normal data commits should create activity, but they are not an independent liveness guarantee.
- **Separate checks:** site reachability, successful scheduler runs, successful source fetches and freshness of each observation are four different facts. A site can be online and stale.
- **Freeze vs revision:** retain the first observed/captured vintage, current revised history and immutable scenarios separately. Decide the exact vintage rule and acceptable release grace periods before enabling unattended publication.
- **Scope:** no need for a paid database, AI API, analytics suite or visitor accounts. GitHub Releases can hold modest source archives; monitor archive growth and keep only changed sources. Blog publishing remains a separate human-authored code/content update.
- **Accounts:** the one-time decisions still needed are the GitHub repository/visibility, Cloudflare account, optional domain, notification subscription and monitoring destination. Credentials go in provider secret stores, never in chat or the repository.
